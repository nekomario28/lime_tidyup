# IK はこの sim で使えるか — 実測と使い方（BT / Python）

Date: 2026-10-20
Status: **使える。ただし「位置のみ」で、シード依存が強い**

対象: `dev2`（`bin/ccc` が起動する `moveit_core.launch.py` 経路）

## 1. 実体：何が IK を解いているか

| 項目 | 実体 |
| --- | --- |
| ソルバ | `kdl_kinematics_plugin/KDLKinematicsPlugin`（`turtlebot3_lime_moveit_config/config/kinematics.yaml`） |
| グループ | `arm`（`joint1`..`joint6` + `end_effector_joint` の**固定ジョイント込みの joint 列**。SRDF に chain 指定なし） |
| ベース / チップ | `base_link` / `end_effector_link`（`lib/actor/system.py` の `base_link_name()` / `end_effector_name()`、pymoveit2 の `MoveIt2(...)` にそのまま渡している） |
| 時間予算 | `kinematics_solver_timeout: 0.05` s、`search_resolution: 0.005` |
| **姿勢** | **`position_only_ik: True`** — 目標クォータニオンは IK で拘束されない |

`roscommon/ws_moveit2` と `turtlebot3_ws` はリポジトリ外（Dockerfile が clone）なので、
SRDF / kinematics.yaml はこの repo には入っていない。上流は
`ROBOTIS-JAPAN-GIT/turtlebot3_lime`(`humble-devel`) の `turtlebot3_lime_moveit_config`。

## 2. 幾何として解けるか（実測）

URDF の腕だけを PyKDL で組み、MoveIt 設定と同じ系統（KDL・関節リミット付き NR）で測定。
再現: `doc/research/probes/2026-10-20_ik_chain_check.py`（手順は同ファイル冒頭）。

```
chain: link1 -> link2 -> link3 -> link4 -> link5 -> link6 -> link7 -> end_effector_link
moveable joints: joint1..joint6 / fixed: end_effector_joint
chain DOF: 6
joint limits (rad): [(-2.827, 2.827), (-1.7, 1.766), (-1.759, 1.857),
                     (-1.571, 1.571), (-1.668, 1.781), (-2.827, 2.827)]
FK at zero (直立): p = (0.0120, 0.0000, 0.4675)  ← 42cm 級の腕
FK→IK 往復（同じ姿勢をシードに）: 40/40 = 100%
到達可能チップ包絡: x[-0.425, 0.443] y[-0.452, 0.459] z[-0.376, 0.465]
最大半径（link1 原点から）: 0.469 m
```

**同じ姿勢をシードにすれば必ず解ける**。一方で、到達可能なチップ 100 点を
**ランダムシード**で解かせると **18/100** しか通りません。6 自由度 NR ソルバの
性質で、シード依存が非常に強い。実務的な意味は次節。

姿勢を含めて解かせた場合（KDL LMA、6 次元）は、同じシードからは
**位置も姿勢も完全一致**する（位置残差 中央値 3.8e-6 m / 姿勢残差 中央値 0.0°）が、
「固定した 90° ピッチ」を要求すると **21/300 しか到達できません** —
つまり腕そのものは姿勢を保持できるが、そのぶん到達域が狭い。

**位置だけを解かせた場合（`position_only_ik: True` の等価物、
`doc/research/probes/2026-10-20_position_only_ik.py`）は 200/200（100%）到達**。
ただし要求姿勢との残差は **中央値 130.0° / 最大 179.7°** — 姿勢は実質的に
「たまたま決まる」だけで、指定できない。

## 3. 使い方（3 層）

### 3.1 既存の使い方＝暗黙の IK（いまのツリーはこれ）

`pymoveit2.MoveIt2.move_to_pose(position=..., quat_xyzw=..., cartesian=False)` が
MoveGroup に pose 目標を送り、その中で IK が走る。

- `lib/actor/system.py:arm_pose(pos, angle)` → `move_to_pose`
- `lib/actor/manipulator.py:move_position(position, orientation)` →
  `run_actor('move_to_pose', ...)`
- `lib/actor/approach_action.py:reach_coke(target)` など

BT XML 側は振る舞い名で呼ぶだけ:

```xml
<ReachObj name="reach_coke"/>     <!-- 座標は behavior 側に固定 -->
<Pick name="pick"/>
<Fit2 name="fit2" distance="[0.175]"/>
```

**現状のツリーから任意座標を IK で指定することはできない**（`ReachObj` は
`__init__(self, name, node)` で座標引数を取らない）。XML 属性は behavior の
コンストラクタ引数に渡る仕組みなので、座標を渡したければ薄い behavior を 1 つ足す。

### 3.2 Python から直接 IK を呼ぶ

`pymoveit2` には **`compute_ik()` がある**（`MoveIt2.compute_ik(position, quat_xyzw, ik_link_name=None, start_joint_state=None, constraints=None, ...) -> JointState|None`）。
IK だけ欲しい（計画しない）用途はこれで足りる:

```python
from pymoveit2 import MoveIt2

arm = MoveIt2(node=node, joint_names=joint_names(),
              base_link_name="base_link", end_effector_name="end_effector_link",
              group_name="arm", use_move_group_action=True)
# 直前の関節状態を渡すのが実質必須（実測でシード無しは 18%）
solution = arm.compute_ik(
    position=(0.20, 0.0, 0.15),
    quat_xyzw=(0.0, 0.0, 0.0, 1.0),          # position_only_ik=True なので姿勢は無視される
    ik_link_name="end_effector_link",
    start_joint_state=arm.joint_state,
)
if solution is None:
    ...  # 到達不能 or シード不良 — fail-closed
```

ROS サービス直叩きでも同じ（`/compute_ik` は move_group が出す）:

```python
from moveit_msgs.srv import GetPositionIK
req = GetPositionIK.Request()
req.ik_request.group_name = "arm"
req.ik_request.ik_link_name = "end_effector_link"
req.ik_request.pose_stamped.header.frame_id = "base_link"
req.ik_request.pose_stamped.pose.position.x = 0.20     # y, z ...
req.ik_request.pose_stamped.pose.orientation.w = 1.0
req.ik_request.robot_state.joint_state = arm.joint_state   # シード
req.ik_request.timeout.sec = 0
client.call_async(req)
```

### 3.3 BT から IK 目標を渡す（推奨：behavior を 1 つ足す）

`pytwb_ws/src/cm1/cm1/behavior/` に 5 行足せば XML から座標指定できる
（XML 属性 → コンストラクタ引数 → `run_actor` の既存パターンと同じ）:

```python
from pytwb.common import behavior
from lib.actor_bt import ActorBT
from math import radians

@behavior
class ReachPose(ActorBT):
    desc = 'move the arm to a Cartesian target (IK)'

    def __init__(self, name, node, x=0.20, y=0.0, z=0.15,
                 roll=0.0, pitch=90.0, yaw=0.0):
        super().__init__(name, 'arm_pose')
        self.target = (float(x), float(y), float(z))
        self.angle = (radians(float(roll)), radians(float(pitch)),
                      radians(float(yaw)))

    def initialise(self):
        super().prepare()
        self.shared.set_callee([('arm_pose', (self.target, self.angle))])
        self.run()
```

```xml
<ReachPose name="reach_above_cube" x="0.20" y="0.0" z="0.15" pitch="90"/>
```

注意: `arm_pose` は `quaternion.from_euler_angles(angle)` で姿勢も渡すが、
`position_only_ik: True` のため**現状この角度は IK に効かない**（下記）。

## 4. 効き方の限界（重要）

1. **姿勢は制御されない。** `position_only_ik: True` なので、`(roll, pitch, yaw)`
   を指定しても IK は位置だけ合わせる。実測（位置のみソルバ、到達可能 200 点）:
   位置は 100% 合うが、要求 90° ピッチとの**姿勢残差は中央値 130.0°・最大 179.7°**。
   `arm_pose(pos, angle)` の角度は実質「助言」でしかない。
   姿勢まで決めたい場合は上流 `kinematics.yaml` の `position_only_ik` を `false` に
   する必要があり、**このリポジトリ外**（`turtlebot3_ws` の設定）なので別判断。
   なお 6 次元で解かせれば姿勢は一致する（実測 0.0°）が、固定姿勢での到達率は
   21/300 まで落ちる。
2. **シード依存。** 単一固定シードでは到達可能点でも 18% しか解けない。
   `compute_ik(..., start_joint_state=...)` に現在の関節状態を渡す、
   または `move_to_pose`（MoveGroup のマルチアテンプト）に任せる。
3. **チップは `end_effector_link`**（`link7` 先 + 固定ジョイント）。グリッパの
   指先ではないので、把持点を狙うときは指先オフセットを足す。
4. 到達範囲は半径 **0.469 m** の球殻。`arm_pose` の既定到達点
   `(0.098, 0, 0.2497)` / `(0.3, 0, 0.05)` はこの内側。

## 5. この repo での「使えるか」の結論

- **IK は既に効いている**（`move_to_pose` 経由）。ただし**位置のみ**。
- **Python からは `compute_ik` が使える**（pymoveit2 / `/compute_ik`）。
  シードを渡すこと。
- **BT XML からは、現状そのままでは任意座標を渡せない**。`ReachPose` のような
  薄い behavior を 1 つ足せば `x/y/z` を XML 属性で指定できる（上記コード）。
- sim 実行時の確認コマンド:

```bash
ros2 service list | grep -E "/compute_ik|/compute_fk"
ros2 param get /move_group robot_description_kinematics.arm.kinematics_solver
ros2 param get /move_group robot_description_kinematics.arm.position_only_ik
```

## 6. ccc2 で「キューブに対して角度付き IK」を実際に使う（実装済み・変更は4つ）

上流の `position_only_ik: True` を実行時に外し、キューブ位置へ**姿勢付き**で腕を向ける。
変更は次の 4 点だけ。

| # | ファイル | 変更 |
| --- | --- | --- |
| 1 | `Dockerfile`（イメージ build 時）| `kinematics.yaml` の `position_only_ik` を `false` へ（`sed` して確認の `grep`、欠けていれば build が失敗）。向きを無視する従来動作に戻すには該当 RUN を外して再ビルド（当時は `bin/ccc2` が起動時に patch し、終了時に trap で戻していた）|
| 2 | `lib/actor/manipulator.py` | actor `arm_to_cube(standoff, roll, pitch, yaw, minimum_confidence)` を追加。`/cube_pose_result` → 最高 confidence の検出 → `pose_3d` が**色解決済み**のときだけ、camera→`base_link` に変換し、`base_link` Z 方向へ `standoff` 上げた点を `arm_pose` へ |
| 3 | `behavior/manipulation.py` | behavior `ArmToCube`（XML 属性 → actor 引数） |
| 4 | `practice_ws/trees/ccik.xml`（当時。dev2 からは削除済み）| 最小ツリー: `SetDestinationByName C` → `SearchCube` → `TakeAim` → `ArmToCube` |

```xml
<ArmToCube name="arm_to_cube" standoff="0.12"
           roll="180.0" pitch="0.0" yaw="0.0" minimum_confidence="0.30"/>
```

```bash
# orientation IK は現在イメージ既定（Dockerfile が position_only_ik を false に patch）
# 従来動作（向きを無視）に戻すには Dockerfile の該当 RUN を外して再ビルド
# 当時はこの測定用の最小ツリー ccik.xml を cm1 のプロンプトから実行していた
# （ccik.xml は roll=180 の幾何が解けず dev2 から削除。orientation IK の実使用例は ccc2）
```

`arm_to_cube` が守る性質:

- **色が解決した姿勢だけ**を使う（鏡像のキューブを狙わない）
- TF が取れなければ**動かさない**（fail-closed、`base_link` 変換待ちを最大 5 秒）
- 目標は「キューブ + `standoff`」で、姿勢は XML 属性のとおり
- 角度は **`position_only_ik: false` のときだけ意味を持つ**（ccc2 が保証）

**未検証**: この変更は lime イメージ（`course_lime-image_yuu`）内でのみ動くため、
手元では**構文・引数・dry-run までしか確認していない**。実機／sim での到達確認、
`roll=180, pitch=0, yaw=0` が「上から掴む」姿勢として正しいかは、sim を起こして
`/cube_pose_result` → `arm_to_cube` のログ（`cube in base_link=... target=...`）で
確かめる必要がある。姿勢の正解は URDF のグリッパ軸（指は link7 の ±Y）依存。

## 7. この文書が主張しないこと

- move_group・コントローラ・Gazebo を通した実行は測っていない（URDF+KDL の
  幾何測定のみ）。「幾何として解ける」ことと「sim が実行して把持できる」ことは別。
- 実機（実 OpenMANIPULATOR）の精度・剛性・把持力は対象外。
- `position_only_ik` を変える判断はこのリポジトリの権限外。
